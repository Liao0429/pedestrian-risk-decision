# RiskEngine 算法审查与优化建议报告

- 审查对象：`src/luckfox_rtsp_yolov5/`（`risk_engine.cc` / `risk_engine.h` / `postprocess.cc` / `yolov5.cc` / `main.cc`）及配套验证脚本 `scripts/crowd_test.py`
- 部署目标：Luckfox Pico Max（RV1106，单核 Cortex-A7 1.2GHz，NPU 1 TOPS）
- 报告日期：2026-10-25
- 优先级定义：**P0**（正确性/可答辩性，必须改）；**P1**（显著提升鲁棒性与输出质量，建议近期改）；**P2**（锦上添花/低风险优化）

---

## 0. 现状摘要

当前风险决策链路为：

```
YOLOv5(RKNN, letterbox 到 640×640)
  → post_process（逐类 NMS，limit_score = box_conf × class_prob 过阈值）
  → main.cc 中只取 COCO class 0(person)
  → 脚点 = 检测框底部中心 (bbox.bottom)
  → mapCoordinates 逆 letterbox 还原到 720×480
  → RiskEngine::addPedestrian() 用固定单应矩阵 H 映射到地面米坐标
  → computeFeatures() 以地面欧氏距离 < 2.0m 建边，计算 n / m / density / r_gcc / clustering
  → evaluate() 规则分级 SAFE / WARNING / DANGER
```

当前规则（`risk_engine.cc:7-13` 的 `#define`）：

```
DANGER : n>=10 && (density>=0.55 || r_gcc>=0.80)
WARNING: n>=5  && (density>=0.28 || r_gcc>=0.55)
否则 SAFE
```

几个关键现状问题（后文逐条展开）：

1. **IPM 单应矩阵 H 是手填的**（`main.cc:74-79` 用假设的源/目标四边形 `getPerspectiveTransform` 生成），并非真机标定，地面米制坐标在比例和透视上都有系统误差，而整个网络建边完全依赖“地面距离(米)”——这是最大的正确性隐患。
2. **代码注释声称“参数可配置”（论文 4.4 节），但阈值全部是编译期 `#define`**，既非 JSON 配置，也无法在真机上现场调参。
3. **当前是单线程流水线**（`main.cc` 的 while 循环串行完成取帧→推理→风险→画框→编码→RTSP），与设计文档声称的“四线程 + 双缓冲”不一致；时序平滑/跟踪/滞回目前完全没有实现，输出会逐帧抖动。
4. **规则阈值与论文表 5-1 的典型值不一致**（n=10/5 vs 表 15/8），答辩时容易被追问。

## 1. 检测后处理（NMS / 置信度 / 类别过滤）对网络特征的影响

**优先级：P0**（漏检直接压低了 `n`，导致 DANGER 判不出）

### 1.1 置信度阈值：固定阈值导致密集场景系统性漏检

- **理由**：`postprocess.cc` 用 `limit_score = box_conf × class_prob`（`process_i8_rv1106`，行 289）过 `BOX_THRESH`（`yolov5.cc:188`，SDK 默认通常 0.25）。人群密集、遮挡、远距离时 person 的置信度显著下降，固定 0.25 会漏掉大量真人 → `n` 被低估。而当前 DANGER 的门槛正是 `n>=10`，若真实 20 人只检出 8 人，系统只会报 WARNING，**漏报风险**。
- **做法**：
  - 为 person 单独设置更低的置信度阈值（如 `conf_person = 0.15~0.20`），宁可多召回、用后续跟踪/时序过滤压制误检（见第 5 节）。
  - 把 `BOX_THRESH` / `NMS_THRESH` / `conf_person` 提为运行时配置（JSON），不要埋在 SDK 头文件里。
  - 用 `scripts/crowd_test.py` 对测试集做 `--conf` 扫描（0.10~0.50），画出 `n / density / r_gcc / 等级` 随阈值的变化曲线，作为论文“准确率表”的量化证据。

### 1.2 NMS：密集人群互相抑制导致“一人一框”欠计数

- **理由**：`nms()`（`postprocess.cc:113-149`）按类做标准 IoU NMS，`NMS_THRESH` 默认一般 0.45。密集人群相互遮挡时 IoU 很高，真实的不同行人会被合并成一个框 → `n` 进一步欠计数，且合并后的脚点位置偏离真实地面点。
- **做法**：
  - 对 person 类单独提高 NMS 阈值（如 0.55~0.60），减少密集场景的抑制；或改用 Soft-NMS。注意这会引入少量重复框，需结合跟踪去重（第 5 节）。
  - 在论文中明确“人群场景下 NMS 欠计数是固有误差”，并给出定量对比（标准 NMS vs 高阈值 NMS 的 `n` 差异）。

### 1.3 类别过滤：通用 COCO 模型对“行人”精度不足

- **理由**：当前用的是 SDK 自带 `yolov5.rknn`（COCO 80 类）。COCO 的 person 类在远距离、部分遮挡、异形姿态上误检/漏检都偏多；误检会凭空增加节点和边（虚高 `n`），漏检则相反。
- **做法**：
  - **推荐（对毕设价值最大）**：用行人数据集（如 COCO person 子集 + CrowdHuman / Pedestrian）微调 `yolov5n`，转 RKNN INT8。这既贴合“行人感知”的标题，又能显著提升 person 类精度。若时间不允许，退而求其次：保持通用模型，但用跟踪 + 置信度加权来抵消误检/漏检（第 4 节）。
  - `post_process` 结果有 `OBJ_NUMB_MAX_SIZE` 上限（SDK 通常 64/128），密集人群会被截断——确认该值，必要时提高。

## 2. 脚点提取 与 IPM 固定 H 的局限、真机标定

**优先级：P0**（核心度量的正确性）

### 2.1 脚点 = 框底中心 的固有误差

- **理由**：`main.cc:186-187` 用 `((left+right)/2, box.bottom)` 作为脚点。问题：
  - 遮挡时框底被截断，不是真实地面接触点；人倾斜时脚点在水平方向上偏离框中心；远景小人框只有几十像素，框底抖动几个像素经 H 映射后地面误差被放大。
  - 这些误差直接进入 2.0m 建边判断，靠近阈值的人对会时连时断，拓扑不稳定。
- **做法**：
  - **首选**：若 NPU 预算允许，改用轻量关键点模型（如 `yolov5n-pose` / `yolov8n-pose` INT8 320×320）取脚踝/足部关键点，比框底更准。若 1 TOPS 跑不动，保留框底方案但加**垂直修正**：真实地面点略高于 `box.bottom`（约为框高的一小比例，因阴影/边缘常使框底越出脚底），`py = bottom - k*height`，`k≈0.02~0.05` 需真机标定。
  - 对每个 track 的脚点做 EMA/Kalman 平滑（第 5 节），抑制单帧抖动。

### 2.2 固定 H 是手填假设，不是真机标定

- **理由**：`main.cc:74-79` 的 H 由 `getPerspectiveTransform` 生成：源四边形 `(0,480),(720,480),(560,300),(160,300)`，目标四边形 `(-3,3),(3,3),(3,-1),(-3,-1)`。这是**纯假设**的“画面底部 6m×4m 地面区域”，与 SC3336 相机实际安装高度/俯仰角/畸变完全无关。结果：
  - 地面米制坐标在比例和透视上系统失真；
  - 失真直接改变 2.0m 建边结果（缩放偏大→边变多→虚高 `density/r_gcc`；偏小→漏边），且随图像行（远近）误差不同，导致“同一物理距离在不同位置判定不同”。
- **做法**：
  - **真机地面标定**：在相机视野内地面上摆放 4 个以上已知间距的标定点（或地面棋盘格），在图像中检测这些点，用 `cv::findHomography`（RANSAC）或 `getPerspectiveTransform`（选 4 个分布良好的点）计算真实 H。
  - H 存成 `H.txt`（3×3 浮点矩阵），运行时由 `RiskEngine::setHomography()` 加载——接口已存在，只需补“从文件加载”路径。
  - 写一个标定小工具（Python，基于 `crowd_test.py` 的框架）：输入标定图像 + 已知地面点坐标 → 输出 `H.txt`；再在真机上摆 1m/2m/5m 参照物验证映射误差，作为论文的标定误差表。
  - 若地面非理想平面（轻微不平），可退化为**按行查表**：将“图像行 y → 距相机米数”和“每行横向米/像素”做成 LUT，成本更低、对非平面更稳。论文中可说明“固定 H + 误差上界分析”。

## 3. 距离阈值 2.0m 的合理性 与 是否自适应

**优先级：P1**

### 3.1 2.0m 本身合理，但硬二值边太脆弱

- **理由**：2.0m 对应社交距离/人际安全距离，论文中可以站得住。但当前是**硬阈值**：1.99m 连边、2.01m 断边。脚点抖动 ±10cm 就能翻转一条边，进而改变 `m / density / r_gcc`，靠近阈值时等级抖动（见第 5 节）。
- **做法**：
  - 把 `EDGE_DIST_M` 从 `#define` 改为运行时配置（JSON）。
  - 引入**软边（加权图）**：边权重 `w = max(0, 1 - d / D_max)`，`D_max=2.0m`。`density` 改为“边权重和 / C(n,2)”，`r_gcc` 用权重图（连通性按 `w>0` 或 `w>0.2` 判定）。这样距离越近贡献越大，且对阈值附近的抖动平滑。
  - 增加**“近距离接触”二级特征**：统计 `d < 1.0m` 的边数（或最小距离），作为边界情况的补充信号/平局裁决器。这与“聚集”告警语义一致。

### 3.2 是否自适应

- **理由**：对静态拥挤评估，固定 2.0m 物理阈值是合理且可解释的；但地面映射误差随距离增大，等效的“建边判定”在远行会失真，且人流场景（走道 vs 聚集）风险语义不同。
- **做法**：
  - 至少做到“**双半径**”：聚集半径 2.0m 用于建边，接触半径 0.8~1.0m 用于强风险特征（近距离接触数）。用两个图，成本仍是 O(n²)。
  - “自适应”不必复杂化：建议**按场景档位配置**（JSON 预设 `gathering` / `walkway` / `platform` 等档位，各有不同 `D_max` 与阈值），而非运行时复杂推断——这样既能应付“是否自适应”的追问，又保持可解释、可复现。

## 4. 网络特征对误检/漏检的敏感性 与 少人数稳定性

**优先级：P1**

### 4.1 `n` 硬门槛最脆弱

- **理由**：DANGER 要求 `n>=10`、WARNING 要求 `n>=5`。边界处（9→10、4→5）一个检测的进出就翻转等级。定量示例（当前阈值）：
  - `n=9, rho=0.60, gcc=0.78` → **WARNING**；`n=10, rho=0.55, gcc=0.80` → **DANGER**。相差一个节点即跨级。
  - `n=5, rho=0.27, gcc=0.54` → **SAFE**；`n=5, rho=0.28, gcc=0.55` → **WARNING**。特征差 0.01 就跨级。
- **做法**：
  - **置信度加权节点**：以 `n_robust = Σ conf_i`（或按置信度归一化）代替原始计数参与阈值比较；低置信度误检（如 conf 0.2）只贡献 0.2 个节点，不轻易推过门槛。同时密度、连通分量也做置信度加权。
  - **时序平滑后再判级**（第 5 节），消除单帧偶然翻转。
  - 在 OSD 上显示“距阈值的余量”（如 `n=9/10 rho=0.30/0.28`），便于现场调试和答辩截图。

### 4.2 少人数时不稳定、且“紧密小群体”永远 SAFE

- **理由**：`n<5` 恒为 SAFE。四个 1 米内紧挨的人（rho 可能 1.0）也报 SAFE——虽然与论文表 5-1 的 SAFE(n=4) 一致，但直观上这是一个值得告警的聚集事件。
- **做法**：
  - 在**复杂网络等级之外**增加一个独立的**“聚集告警 GATHER”**（正好对应设计文档最初的四告警方案之一）：`n>=3 且 存在边距<1.0m 的连通簇` → 触发 GATHER。它与论文的网络等级并存，不冲突、可解释，答辩时作为“多级告警联动”加分项。
  - 若不想加新告警，可加“紧密小群体覆盖”：`n>=3 且 rho>=0.7 且 r_gcc>=0.8` → 至少 WARNING（需在论文中说明这是对表 5-1 SAFE(n=4) 的补充，避免矛盾）。

## 5. 时序稳定性：多帧平滑 / 跟踪 / 滞回

**优先级：P0**（直接决定输出是否可用、演示是否可信）

### 5.1 现状：完全无状态，逐帧抖动

- **理由**：`main.cc:182` 每帧 `riskEngine.clear()`，单帧结果直接判定。检测抖动（某帧漏检）、脚点抖动（靠近 2.0m 阈值）、置信度临界波动都会让等级在 SAFE/WARNING/DANGER 间闪烁。此外推理偶发掉帧/无检测时，`n=0` 直接判 SAFE，会造成“本来 DANGER 突然绿一下”的错误。
- **做法**（按性价比排序）：
  1. **等级滞回（hysteresis）状态机**：维护上一等级。升级需连续 K 帧满足新等级（如 K=3）；降级需连续 M 帧满足更低等级（如 M=5，或“5 帧中 3 帧”）。彻底消除单帧闪烁。
  2. **特征 EMA 平滑**：对 `n / density / r_gcc` 做指数滑动平均（`alpha≈0.4~0.6`）后再判级；`n` 可先平滑为浮点再参与阈值比较（配合 4.1 的置信度加权）。
  3. **无数据保持**：推理返回 0 检测时，不立即回 SAFE；保持上一等级至多 5 帧/1 秒，并在 OSD 打 `no-data` 标记。
- **实现注意**：当前主循环是单线程，平滑状态可直接挂在 `RiskEngine` 成员（把类从纯函数式改成带内部状态），无需引入多线程即可落地。

### 5.2 轻量跟踪：一石多鸟

- **理由**：设计文档承诺了“IoU 简易跟踪”（用于滞留/速度告警），但代码未实现。加入跟踪后可获得：
  - **误检抑制**：只把“连续出现 ≥2~3 帧的 track”计入节点，瞬时误检直接过滤；
  - **脚点平滑**：对每个 track 的脚点做 EMA/Kalman，稳定 2.0m 阈值附近的边；
  - **支持滞留/速度告警**：补齐论文的 LOITERING / FAST_MOVE，丰富功能面。
- **做法**：
  - 实现一个轻量 IoU/质心匹配跟踪器（`n≤64` 时匈牙利/贪心匹配都是微秒级），每帧更新 track 表；决策线程读取 track 表而非原始检测。
  - 跟踪器输出：`person_id, smoothed_foot(m), conf, track_age, speed`。
  - 论文“时序稳定性”一节就有量化素材：统计平滑前后等级翻转次数/滞留时长。

## 6. 规则阈值 与 论文表 5-1 的一致性

**优先级：P0**（学术一致性与可答辩性）

### 6.1 数值矛盾

论文表 5-1（各等级典型特征值）与代码阈值对照：

| 等级 | 表5-1 典型值 (n, rho, gcc) | 代码阈值（`risk_engine.cc`） | 一致性结论 |
|------|------------------------------|------------------------------|------------|
| SAFE | (4, 0.17, 0.50)              | `n<5` → SAFE                 | 基本一致（n=4 恒 SAFE；gcc=0.50 低于 0.55 的 WARNING 门槛，OK） |
| WARNING | (8, 0.39, 0.63)          | `n>=5 && (rho>=0.28 \|\| gcc>=0.55)` | **不一致**：代码的 n、rho、gcc 门槛都比表 5-1 的 WARNING 典型值更松 |
| DANGER | (15, 0.68, 0.87)           | `n>=10 && (rho>=0.55 \|\| gcc>=0.80)` | **不一致**：代码的 n、rho、gcc 门槛都比表 5-1 的 DANGER 典型值更松 |

即：**代码比论文更“敏感”**。答辩时评审若拿表 5-1 对照代码 `#define`，会质疑阈值来源。

### 6.2 语义澄清：表 5-1 是“典型值”而非“判定阈值”

- **理由**：表 5-1 的数值更像各等级的“代表/均值样本”，而代码里的规则是“判定边界”（≥门槛）。两者本不必相等，但论文必须把语义写清楚，且边界最好与典型值自洽。
- **做法（二选一）**：
  - **方案 A（推荐，改动小且自洽）**：用表 5-1 导出判定边界——
    - `DANGER: n>=15 && (rho>=0.54 || gcc>=0.75)`（rho/gcc 取 WARNING 与 DANGER 典型值的中点：`(0.39+0.68)/2≈0.54`，`(0.63+0.87)/2≈0.75`）
    - `WARNING: n>=8 && (rho>=0.28 || gcc>=0.55)`（与表 5-1 的 n=8 对齐）
    - 论文写：“表 5-1 给出各等级典型特征；判定阈值取相邻等级典型值中点，保证类间可分。”
  - **方案 B**：保持代码阈值不变，但在论文中**新增一张“判定阈值表”**，并明确区分“表 5-1 典型特征值”与“表 5-2 判定阈值”，用 `crowd_test.py` 在测试集上验证所选阈值能复现表 5-1 的分级。
- **必做**：无论选哪个方案，把阈值从 `#define` 改为**运行时 JSON 配置**（`risk_config.json`），在论文附录列出，落实“参数可配置”的承诺，也便于现场调参复现。

## 7. 边缘端性能：O(n²) 在单核 1.2GHz 是否可接受

**优先级：P2**（RiskEngine 本身性能无虞，重点在别处）

### 7.1 复杂度与实测估算

- `computeFeatures()` 的复杂度：距离矩阵 `O(n²)`，BFS 连通分量最坏 `O(n²)`，平均聚类系数最坏 `O(n³)`（完全图时每节点邻居 k≈n，内层 `k²`）。
- 单核 A7 1.2GHz（约 0.5~1 GIPS）下的粗略估算（完全图最坏情形）：

| n（节点数） | 距离 sqrt 对数 | 聚类最坏内层迭代 | 估计耗时 |
|------------|---------------|------------------|----------|
| 16  | 120  | 3,600  | ~0.02 ms |
| 32  | 496  | 30,752 | ~0.14 ms |
| 64  | 2,016 | 254,016 | ~1.1 ms |
| 100 | 4,950 | 980,100 | ~4.4 ms |
| 128 | 8,128 | 2,064,512 | ~9.3 ms |

- **结论**：实际 `n` 受 `OBJ_NUMB_MAX_SIZE`（SDK 通常 64/128）限制，人群场景 `n≤64` 时 RiskEngine 最坏约 1ms，决策线程 1~5Hz 下 CPU 占用可忽略。**O(n²)/O(n³) 完全可接受，不是瓶颈。**

### 7.2 真正的瓶颈与隐患

- **每帧堆分配**：`computeFeatures()` 每帧 `new` 两个 `n×n` 的 `vector`（`adj` + `dist`），256MB 内存 + DMA 缓冲下反复分配/释放会造成碎片与不确定延迟。
  - **做法**：预分配成员级固定缓冲区（如 `MAX_N=128` 的位图邻接 + 距离数组），每帧复用；`n` 超过 `MAX_N` 时截断并打日志。
- **平方根可省**：距离比较可改为 `d² < EDGE_DIST_M²`，省掉 `sqrt`（微优化，顺手做）。
- **单线程流水线（更大的问题）**：当前 `main.cc` 是单线程循环，风险决策、画框、H264 编码、RTSP 全串行，且 `letterbox()` 硬编码 640×640。若模型实际是 320×320（设计文档写 320），`letterbox` 会填 640 造成输入尺寸不匹配且白白多算 4 倍——**请先核对 `init_yolov5_model` 读到的 `model_width/model_height` 与 `main.cc` 全局 `model_width=640` 是否一致**。
  - **做法**：论文若写“四线程”，就应真正实现线程分离；至少把决策从推理/编码主循环中解耦（决策线程 1~5Hz），RiskEngine 那 1ms 完全不影响帧率。时序滞回/跟踪状态也正好挂在独立决策线程上。

## 9. 最值得先做的改进（TOP 5）

1. **真机地面标定，替换手填 H**（R1，P0）
   理由：整个建边、密度、连通分量的正确性都建立在“地面米制坐标”上，H 错则一切皆错。标定工具 + 文件加载接口改动量不大，却是正确性的根基。

2. **规则阈值对齐论文表 5-1 并改为 JSON 配置**（R2，P0）
   理由：代码与论文数值不一致是答辩时的直接风险点。按“相邻典型值中点”导出 DANGER/WARNING 边界，或新增“判定阈值表”并在论文中澄清语义，同时落实“参数可配置”承诺。

3. **时序滞回 + 特征 EMA + 无数据保持**（R3，P0）
   理由：无需跟踪即可大幅消除单帧抖动，让演示输出稳定、可信；改动只在 RiskEngine 内部加状态，成本最低、见效最快。

4. **轻量 IoU/质心跟踪**（R4，P0）
   理由：一石多鸟——过滤瞬时误检、平滑脚点（稳定 2.0m 边）、支撑滞留/速度告警，补齐设计文档承诺的四告警能力，是论文“风险决策”创新点的重要支撑。

5. **person 单独置信度 + 类别专用 NMS 阈值**（R5，P0）
   理由：直接缓解密集/遮挡场景的欠计数，避免真实高危场景因 `n` 不足被误判为低风险。改动小、收益直观。

> 若时间有限，先做 **R1 → R2 → R3** 三条（正确性 + 可答辩性 + 稳定性），已足以让系统“能看、能讲、能稳定演示”；R4/R5 作为下一步增强。

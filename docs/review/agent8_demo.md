## 二、具体建议清单（每条含证据路径 / 价值 / 成本）

### 建议 1：现场"制造"真实 DANGER 触发 —— 人群图片/平板入镜（最优先）
- **做法**：从 `dataset/images500/` 选 1~2 张高密度聚集图（如 14+ 人，README 统计这类检出率 76.7%），打印成 A4 或平板显示，答辩时放到镜头前，实时画面即可出现 WARNING/DANGER 过渡。
- **证据路径**：`dataset/images500/`（真实 COCO 图）→ 触发后 `rtsp://板IP:554/live/0` 与 `http://板IP:1984` 实时显示红色 DANGER 顶条 + 检测框。
- **价值**：把"摄像头前无人"的死局变成主动可控的现场演示；同时证明端到端链路（真实图像 → NPU → 决策 → 推流 → 网页）。
- **成本**：极低（打印费几元 / 平板已有）。唯一风险是光照与角度，答辩前必须实测 1~2 张图，确认能稳定触发 DANGER。

### 建议 2：用 go2rtc 注入本地视频流作为实时兜底（强烈推荐）
- **做法**：在 `go2rtc.yaml` 的 `streams` 里增加一条文件流（如 `demo: ffmpeg:results/demo/mixkit_13192_enhanced.mp4#loop=1`），网页端可同时切到这条"实时循环视频流"，画面自带 DANGER 过渡。
- **证据路径**：`docs/WEB_VIEWER.md` 中的 go2rtc 配置（`streams.cam` 处扩展）；视频素材 `results/video_enhanced_fsm/mixkit_13192_enhanced.mp4`。
- **价值**：即使镜头前无人、也没有照片，网页上仍能展示风险切换，且观众可自行点开，互动感强。
- **成本**：低（改 yaml 加一行 + 开发板验证）。注意：需提前确认 go2rtc 该版本 `file/ffmpeg` 源在 armv7 上可用。

### 建议 3：新增一张"算法原理时序曲线图"用于答辩 PPT（高杠杆）
- **做法**：写 ~50 行绘图脚本（复用 `scripts/plot_results.py` 的 matplotlib 风格），读取 `results/video_enhanced_fsm/mixkit_13192_timeline.json`，把 `level`（分档）、`n`、`rho`、`fiedler` 随帧画出 4 条曲线，并标注 FSM 的 SAFE→WARNING→DANGER 切换点与滞回/保持区间。
- **证据路径**：`results/video_enhanced_fsm/mixkit_13192_timeline.json`（已有每帧数据，无需重新跑模型）。
- **价值**：一张图同时讲清"聚集分析（rho/fiedler 上升）+ 时序稳定（等级曲线几乎不闪跳）"，是回答"FSM 为什么有价值"最有力的材料，胜过口播十句。
- **成本**：低（脚本 + 出图，1~2 小时）。

### 建议 4：实时网页增加"状态曲线"（可选加分项，非必须）
- **做法**：在 `main.cc` 已每帧 printf 的字段基础上，同时把最新 `level/n/rho/r_gcc/fiedler` 写到一个轻量 JSON 接口（如 `/tmp/status.json` 或由 go2rtc 转发），前端（go2rtc 页面或自写静态页）轮询并画滚动曲线。
- **证据路径**：`main.cc` 第 345-346 行已有字段输出；`docs/WEB_VIEWER.md` 提到 go2rtc 有 `/api/streams`，可类比扩展。
- **价值**：实时展示"等级曲线稳定"与"特征变化"，比离线图更有现场冲击力。
- **成本**：中（改 C++ + 重新交叉编译部署 + 前端）。**建议优先级放低**：答辩只有几分钟，若时间紧，用建议 3 的离线图即可。

### 建议 5：画面叠加"IPM 鸟瞰小窗"（核心创新点的可视化）
- **做法**：在画面右下角加一个小 ROI，把已算出的地面米制脚点 `groundPts` 画成俯视散点图（叠加 2m 建边连线），实时显示"透视画面 → 地面米制拓扑"的对应关系。
- **证据路径**：`main.cc` 已有 `groundPts` 与单应矩阵 `H`；`docs/SYSTEM_PRINCIPLE.md` 2.3 节讲"10 人分散 vs 6 人聚集"是核心创新。
- **价值**：直接回答"IPM 几何校正 + 图论拓扑到底解决了什么"——评委一眼看懂透视畸变如何被校正、聚集如何被识别。
- **成本**：中（改 C++ 叠加逻辑 + 重编译部署）。若时间紧，可先在离线处理脚本（`scripts/crowd_test_enhanced.py`）里加鸟瞰小窗生成演示视频，开发板保持现状。

### 建议 6：现场演示"活的真机证据"——SSH/串口操作展示（低成本高说服力）
- **做法**：答辩现场用 SSH（或串口）连开发板，依次执行并投屏：
  1. `ss -tlnp | grep -E '554|1984'` → 显示端口监听
  2. `ps aux | grep luckfox` → 进程存在
  3. `top -bn1 | head` → CPU 占用
  4. `tail -5 /tmp/demo_rtsp.log` → 看到 `[EnhancedDecision] level=...` 实时滚动
- **证据路径**：`scripts/start_demo.sh` 已把日志写到 `/tmp/demo_rtsp.log`；`EDGE_TEST_REPORT.md` 的"复现"节给了命令。
- **价值**：用"活的终端输出"证明程序真的在板子上跑，而不是预录视频，这是评委最买账的证据。
- **成本**：低（提前配好 SSH/串口 + 一条命令脚本）。建议做成一张 A4 速查卡放桌上。

### 建议 7：抓一张"手机浏览器打开网页看到实时画面"的照片进 PPT
- **做法**：用手机浏览器打开 `http://板IP:1984`，截屏；旁边放开发板硬件照片，合成一张"端到端链路"图。
- **证据路径**：`docs/WEB_VIEWER.md` 访问地址；开发板实物。
- **价值**：证明摄像头→NPU→决策→RTSP→go2rtc→浏览器全链路打通，且是无线/局域网真实访问。
- **成本**：低。

### 建议 8：修复启动日志噪音（一行改动）
- **做法**：`main.cc` 第 81 行 `system("RkLunch-stop.sh");` 改为先判断存在或加 `2>/dev/null`（如 `system("RkLunch-stop.sh 2>/dev/null");`），避免启动时打印 `not found`。
- **证据路径**：`src/luckfox_rtsp_yolov5/src/main.cc:81`；当前日志首行即为该报错。
- **价值**：消除评委眼中的"工程粗糙"观感。
- **成本**：极低（一行 + 重编译部署）。

### 建议 9：准备"风险等级与阈值"速查页，应对评委提问
- **做法**：把 `config/default_config.json` 的关键阈值（n=10 / rho=0.55 / gcc=0.8 进 DANGER；FSM 滞回 up=0.65/down=0.55、confirm=3/5、danger_hold=10 帧）做成一页"决策规则表"。
- **证据路径**：`config/default_config.json` 的 `danger/warning/fsm` 块。
- **价值**：评委常问"凭什么判 DANGER？阈值怎么来的？"——一页纸直接回答，并体现"阈值可配置"工程化。
- **成本**：低。

## 三、现场演示故障与备用方案

| 故障场景 | 现象 | 备用方案（按优先级） |
|---|---|---|
| 镜头前无人，网页一直 SAFE | 网页全绿，无风险切换 | ① 人群照片/平板入镜（建议 1）；② 播放预录 mixkit_13192（`docs/DEMO_VIDEO.md`）；③ go2rtc 注入文件流（建议 2）；④ 请现场观众站到镜头前走动 |
| 无线/局域网不稳，网页卡顿 | go2rtc 转圈、延迟大 | ① 网线直连开发板；② 手机开热点让开发板连（硬件扩展方案里的 WiFi 思路）；③ 退到本地播放预录视频 |
| 开发板开机后服务未起 | 网页/RTSP 打不开 | `start_demo.sh` 已有 40s/30s 超时提示；答辩前把启动命令写入 `/etc/rc.local` 或 systemd 上电自启，并用 `ss -tlnp` 快速诊断 |
| 检测框闪跳 / 误检 | 等级来回跳 | 用光照正常的场景/图片（README 已诚实说明低照度漏检边界）；不要承诺"零误报" |
| 现场嘈杂，语音告警听不清 | 语音播报被淹没 | 用三色 LED / 屏幕等级显示替代声音告警（声音作为辅助） |
| 预录视频在电脑播放卡顿 | 编码/解码问题 | 提前转成 H.264 MP4 并在演示电脑上实测播放 |

## 四、扩展投入建议：值得做 vs 应停止

### ✅ 值得投入（低成本高展示价值，答辩前优先）
1. **三色 LED 等级指示灯**：`docs/hardware/HARDWARE_EXPANSION_PLAN.md` 中成本最低（几元），绿/黄/红对应 SAFE/WARNING/DANGER，视觉冲击强，几行 GPIO 代码。
2. **DANGER 单向语音播报（TTS）**：保留"危险时播报"这一半，砍掉复杂的语音识别（ASR）——单向播报实现简单、不易翻车，且现场演示效果好。
3. **算法原理时序曲线图 + IPM 鸟瞰小窗**（建议 3/5）：直接提升"讲清算法"的能力。

### ⛔ 建议停止投入（答辩前避免，工程量大或现场易翻车）
1. **触摸屏 LVGL 动画菜单**（`docs/hardware/touchscreen.md`）：LVGL 菜单 + 缩略图 + 触控交互工程量巨大，现场演示易出 bug，且与"风险决策"主叙事关联弱。**作为"已设计/预留接口"讲即可，不上实机。**
2. **双舵机云台跟踪**（`docs/hardware/tracking_servo.md`）：机械结构 + 加长排线易缠绕/抖动，现场演示风险高；且与"聚集分析"主逻辑关联弱。**保留方案文档，不做实机。**
3. **离线语音识别 ASR**（`docs/hardware/voice_module.md`、`LUCKFOX_VOICE_ASSISTANT_PLAN.md`）：sherpa-onnx 中文识别在 armv7 上部署复杂，现场嘈杂环境识别率低，翻车概率大。**降级为单向 TTS 播报。**
4. **充电宝移动供电/无线化**：锦上添花，答辩非必需，若时间紧可完全不做。
5. **继续扩展硬件大类**：硬件已不是答辩瓶颈，瓶颈是"如何把已有真机证据讲清楚 + 现场能主动演示 DANGER"。**把剩余时间投入建议 1/3/6/8，收益最高。**

## 五、答辩自问清单（提前演练）

1. "实时画面为什么一直是 SAFE？你能现场触发一次 DANGER 吗？"——必须有可控手段（照片/平板/文件流）。

## 六、总结要点

- **已有真机证据很扎实**（12.5MB/42.5%/6.9FPS/截图/573 条日志），答辩基础没问题，缺的是"现场主动展示 DANGER 的手段"与"算法原理的可视化"。
- **最高优先级**：①现场用人群图片/平板触发真实 DANGER；②go2rtc 注入视频文件流作实时兜底；③做一张时序曲线图讲 FSM 稳定；④现场 SSH 展示活的日志/进程。
- **最低成本修复**：`main.cc:81` 的 `RkLunch-stop.sh not found` 启动噪音，一行改动。
- **停止投入**：触摸屏 LVGL、双舵机云台、离线 ASR、移动供电——方案文档已足够，答辩前不再上实机。
- **核心原则**：把"证明程序真在设备上跑 + 现场能演示风险切换 + 一张图讲清时序稳定"作为答辩前三天的一切投入方向。

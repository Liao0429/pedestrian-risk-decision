## 质疑 1：『两人 0.7067 DANGER vs 三人链 0.61 WARNING』定为 P1，从产品/决策系统角度是否应升级为 P0？

### 1.1 质疑点
A2 在第五节结论中明确写「**无 P0 问题**（无崩溃、无数据损坏、无生产主链路不可用）」，把评分倒挂列为 P1-1；但同一份报告又承认它是「最可能被评审/答辩质疑的点」。对一款**输出物就是风险等级**的决策系统而言，主链路等级语义错误是否应视为「生产主链路不可用」？A2 的 P0 判据是否适用？

### 1.2 判断：**应升级为 P0（至少 P0-答辩阻断项），A2 的 P0 判据不适用**

实算复现（Python，`risk_fsm.py` 默认配置 w1=0.4/w2=0.3/w3=0.3/w4=0.1/n_ref=20/up_danger=0.65）：

| 输入 | n | density | r_gcc | fiedler | score | 等级 |
|---|---|---|---|---|---|---|
| 单人 [(1,2)] | 1 | 0 | 0 | 0 | 0.0200 | SAFE |
| 两人相距 0.5m | 2 | 1.0 | 1.0 | 2.0 | **0.7067** | DANGER（3 帧后） |
| 两人相距 1.5m | 2 | 1.0 | 1.0 | 2.0 | **0.7067** | DANGER |
| 两人相距 2.0m | 2 | 0 | 0.5 | 0 | **0.1900** | SAFE |
| 三人链 1.5m | 3 | 0.667 | 1.0 | 1.0 | **0.6100** | WARNING |
| 三人全连 1.5m | 3 | 0.667 | 1.0 | 1.0 | **0.6100** | WARNING |

A2 的核心数值（0.7067 / 0.61 / 0.02）全部复现成立。但 P0 判据应修正：

1. **问题就发生在生产主链路**：`enhanced_decision.cc:140-178` 的 `processFrame` 就是 `smoothPoints → graph_laplacian → risk_fsm`，`enable_risk_engine_fallback=false`（`default_config.json:20`）意味着 FSM 是**唯一**生产决策路径。FSM 输出错误等级 = 主链路输出错误，这正是「生产主链路不可用」，不是边缘模块问题。
2. **触发条件极常见**：默认 `edge_dist_m=2.0`，任何两名行人间距 <2m（人行道并排、排队、交谈、候车）都会以 score=0.7067 进入 DANGER 判定，`confirm_up=3` 帧后升级，再被 `danger_hold_frames=10/danger_hold_ms=1000`（`risk_fsm.py:288-302`）保持至少 1 秒。这不是病态输入，是日常场景。
3. **与规则引擎语义直接冲突**：`risk_config.h:50` 默认 `danger.n=10`、`risk_engine.cc:106-107` 要求 `n>=10` 才 DANGER。同一份配置里两条决策路径对「DANGER 需要多少人」给出互相矛盾的定义，且默认走的是 FSM 这条错误路径。
4. **答辩可现场复现**：评委只需摆两个脚点（甚至现场两个人站一起）就能打出 DANGER。A2 自己也承认这是「最可能被评审/答辩质疑的点」——既然预判会被当场质疑，就不应停留在 P1。
5. **A2 未覆盖的更隐蔽触发源——重复点**（见质疑 3）：同坐标重复点 score=0.7067，直接 DANGER。这把 P1-1 从「理论校准倒挂」升级为「检测层一次重复框就误报」的工程必现问题。

### 1.3 建议
- 将 P1-1 升级为 **P0**，理由按上述 5 条归档（主链路唯一决策路径 + 常见输入触发 + 与规则引擎语义冲突 + 答辩可现场复现 + 重复点放大）。
- 答辩前必须完成修复；若时间不允许，至少准备「两人紧邻 DANGER」的现场口径与消融数据，避免被评委当场问倒。
- 顺带修正 A2 报告中的一处数值错误（见质疑 5）。

## 质疑 2：『DBSCAN 标签反转（C++ NOISE=-1 vs Python -2）』的实际触发条件与修复成本？

### 2.1 质疑点
A2 将标签反转定为 P1-2，说「数据契约不一致，未被任何测试捕获」。实际触发条件是什么？修复到底要动几个文件？A2 给出的修复范围（统一哨兵值 + 修正 docstring）是否完整？

### 2.2 判断：**事实成立，但 A2 漏掉了最关键的『假测试防线』，修复成本比 A2 说的多一处**

- **事实确认**：`crowd_dbscan.py:34-35`（`UNCLASSIFIED=-1, NOISE=-2`）与 `crowd_dbscan.h:107-108`（`NOISE=-1, UNCLASSIFIED=-2`）确实反转；实算 `dbscan_labels([(0,0),(5,0)], 1.0)` 返回 `[-2,-2]`，C++ 侧返回 `[-1,-1]`。A2 描述正确。
- **实际触发条件**：`crowd_dbscan` 当前无生产消费（README 标注可选扩展），只有 `tests/test_crowd_dbscan.py` 消费。因此反转**目前不产生运行时错误**，只在「未来跨语言集成/比对脚本按 `label==-1` 判断噪声」时出错。P1 定级合理。
- **A2 漏报的关键事实**：`tests/test_crowd_dbscan.py:366-379` 声称「逐行复刻 crowd_dbscan.h 验证一致」，但其复刻函数硬编码 `UNCLASSIFIED, NOISE = -1, -2`——与真实 C++ 头文件（`NOISE=-1, UNCLASSIFIED=-2`）**恰好相反**。也就是说，这条本应发现反转的测试，因为复刻版沿用了 Python 的哨兵值而「自证一致」，形成虚假安全感。A2 说「未被任何测试捕获」是对的，但没说清**是测试本身被带偏了**。答辩时若被问「为什么测试没抓到」，必须答出这一层。
- **修复成本（低，但不止 A2 说的两处）**：
  1. `crowd_dbscan.py:34-35` 常量：`UNCLASSIFIED=-2, NOISE=-1`（与 C++/sklearn 惯例对齐）；
  2. `crowd_dbscan.py` docstring 三处（`:16`、`:58`、`:128`），A2 只提了 :128，漏了 :16 模块 docstring 同样写「-1 表示噪声」，:58 的「NOISE(-2)」也要同步改；
  3. **`tests/test_crowd_dbscan.py:379` 复刻版常量**必须同步改为 `UNCLASSIFIED, NOISE = -2, -1`，否则修复后该测试会以「错误方式」报失败；
  4. 若按 A2 的 P1-4 建议补跨语言黄金用例，还需改 `scripts/generate_golden.py` 增加 dbscan 生成器 + C++ 侧新增测试目标——这部分成本中等，且 C++ 侧目前确实没有 crowd_dbscan 测试目标（`src/luckfox_rtsp_yolov5/tests/` 下无对应文件，已核实）。

### 2.3 建议
- 接受 P1-2，但修复范围扩为 **4 处**（Python 常量 + 3 处 docstring + 测试复刻版常量），并新增一条跨语言黄金用例锁定 labels 原值（与 P1-4 合并做）。
- 在评审记录中主动说明「现有复刻测试的哨兵值用错」这一事实，防止它继续掩盖未来分歧。

## 质疑 3：『幽灵点』的严重度——A2 只分析了一半

### 3.1 质疑点
A2 的 P1-3 只覆盖「Kalman 漏检外推幽灵点」（Python 输出含漏检外推点、C++ 排除）。但任务关注的是「**疑似重复点导致图拉普拉斯错误**」——即两个行人脚点重合/几乎重合时，图拉普拉斯把它们当作两个节点并连零距离边。A2 对后者只字未提。两半各是什么严重度？

### 3.2 判断：**A2 的 P1-3 属实且影响论文数据；重复点导致图拉普拉斯错误是 A2 漏报的高危问题，且直接喂给 P1-1**

**前半（A2 的 P1-3，确认属实）**：
- `kalman_tracker.py:323-327`（`_predict_all` 对全部轨迹外推）、`:414-416`（`states()` 返回所有轨迹含漏检外推）；消费端 `scripts/crowd_test_enhanced.py:110-111` 与 **`scripts/ablation_study.py:73-75`（论文消融脚本）** 都全量使用 `states().values()`；C++ `enhanced_decision.cc:52-138` 只输出「匹配修正点 + 新建点」，未匹配轨迹仅 `miss++`。
- 触发条件：任意一帧漏检（YOLO 置信度抖动、遮挡、目标出画前），Python 侧 n/density/r_gcc 因外推点保持偏高，C++ 侧立即下降，双端 FSM 等级分叉。
- 严重度：**P1 偏低，建议至少与 P1-1 同批处理**。因为它直接污染 `ablation_study.py` 产生的论文消融数据——论文里「Kalman 平滑 vs 不平滑」的对比数字建立在 Python 独有语义上，板端复现不出同等结果，这是答辩的「论文可复现性」雷区。

**后半（A2 漏报：重复点导致图拉普拉斯错误）**：
- 实算（`graph_laplacian.py` 对同坐标点建边 `dist=0 < edge_dist`，`build_adjacency` 无去重）：

| 输入 | n | m | density | r_gcc | fiedler | score | 等级 |
|---|---|---|---|---|---|---|---|
| 重复点 [(0,0),(0,0)] | 2 | 1 | 1.0 | 1.0 | 2.0 | **0.7067** | DANGER |
| 三人含重复 [(0,0),(0,0),(1.5,0)] | 3 | 3 | 1.0 | 1.0 | 3.0 | **0.7350** | DANGER |

- **C++ 生产链不去重**：`smoothPoints` 中同一观测被轨迹匹配后，另一份相同观测会作为「未匹配点」新建轨迹（`enhanced_decision.cc:114-124`），输出仍是两个重合点 → 板端同样 DANGER。
- 触发条件：YOLO 重复框（NMS 未完全抑制）、遮挡边缘同一人被检出两次、IPM 逆变换后两脚点落入同一网格/像素。这些都是真实检测场景，不是构造输入。
- 严重度：**这是 P1-1 的具体工程触发源，比「两人相距 0.5m」更隐蔽**——答辩演示视频里只要出现一次重复框，系统就报 DANGER 且保持 1 秒，评委不会认为这是「理论校准问题」，而会认为是「系统乱报」。

### 3.3 建议
- 将「重复点/重合点」作为 P1-1（P0）的**独立触发子项**纳入修复范围：建边前对距离 < 去重阈值（如 0.05m）的脚点合并，或在 FSM 对 n<3 完全重合图做门控。
- 黄金数据补充重复点用例（graph_laplacian.json 现有 6 个用例全部是互异点，无任何重合/重复点覆盖）。
- P1-3 修复（`states(include_missed=False)`）应同步评估对 `ablation_study.py` 输出数据的影响，论文结果需重新生成并记录差异。

## 质疑 4：A2 的修复方案是否涉及算法口径变化？会不会影响已有黄金数据/测试？

### 4.1 质疑点
A2 对 P1-1 给出四条修复建议（① 提高 n_ref 或增大 w1；② 谱项/密度项对 n<3 门控；③ 修改 density 归一化；④ 文档/消融补充），但**没有评估任何一条对现有黄金数据、C++ 黄金测试、规则引擎口径的影响**。逐一判断。

### 4.2 判断：**①③ 是高风险口径变化且会破坏黄金数据；② 是语义口径变化但现有黄金不受影响；A2 未做回归影响分析本身是失职**

- **① 提高 n_ref（如 30-50）或增大 w1 —— 口径变化，n_ref≥50 会翻转现有黄金用例**：
  `risk_fsm.json` 的 `ladder_up_down_with_dual_hold` 用例（n=15, density=0.8, r_gcc=0.9）：当前 score=0.81 → DANGER；n_ref=30 时 score=0.71（仍 DANGER 但余量从 0.16 缩到 0.06）；**n_ref=50 时 score=0.63 → 低于 up_danger=0.65，期望等级从 DANGER 翻转为 WARNING，黄金测试必挂**。A2 建议的「30-50」区间上沿直接踩雷。增大 w1 同理会整体移动所有 FSM 输出，`hold_without_timestamp`、`hysteresis_band` 用例也需重新核算。
- **② 谱项/密度项对 n<3 门控 —— 语义口径变化，但现有黄金用例不受影响**：
  `risk_fsm.json` 中 n=2 的帧（hysteresis_band 第 3 帧 n=2, density=0.1, r_gcc=0.1）score=0.07，远离阈值，门控后仍 SAFE；graph_laplacian 黄金用例不含 FSM。**这是四条里对现有测试最安全、且能直接压住 P0 的方案**，但属于「两人不可能 DANGER」的语义变更，需新增 2 人/3 人黄金用例锁定。
- **③ 修改 density 归一化 —— 最大口径变化，整体推翻黄金数据与规则引擎**：
  `density = m/(n(n-1)/2)` 同时被 `graph_laplacian.py:159`、`graph_laplacian.h:246`、`risk_engine.cc:65`、`crowd_test.py::compute_features` 使用；`graph_laplacian.json` 全部 6 个用例的 density 期望值都基于该公式；规则引擎阈值 `danger.rho=0.55/warning.rho=0.28` 也是在这个口径下标定的。改公式 → 黄金数据整体失效、C++ 黄金测试全挂、规则引擎阈值语义漂移、论文消融数据不可比。**强烈反对作为短期修复**。
- **④ 文档/消融补充 —— 零代码影响，安全，但只能作为 P0 的过渡口径，不能替代修复**。
- **A2 的元问题**：A2 在 P1-4 里强调「测试覆盖缺口」，但自己提修复方案时完全没做「修复对现有黄金回归的影响分析」。这份报告会被拿去答辩，评委可能追问「你建议改 n_ref，黄金测试怎么办」——A2 目前答不上来。

### 4.3 建议
- P0 修复组合采用 **②（n<3 门控 w4 谱项 + 限制 density 权重）+ ④（文档化语义边界）**；n_ref 如要微调（≤30）必须先跑黄金回归确认不翻转等级。
- **禁止采用 ③**；如确实需要重定义 density，必须作为独立 RFC，同步更新 Python/C++/规则引擎阈值/黄金数据/论文消融，并重跑全部测试。
- 任何口径变化落地流程：同步改 `risk_fsm.py` + `risk_fsm.h` + `default_config.json`（+ `risk_config.h` 校验），`scripts/generate_golden.py` 重新生成黄金，重跑 Python 黄金回归 + C++ 黄金测试，并新增 2 人/3 人/重复点/NaN 用例。

## 质疑 5（事实勘误）：A2 报告的边界跳变数值错误

A2 在 P1-1 根因中写「两人距离恰好 ≥2m 时无连边 → score=0.04（SAFE），在 2m 边界产生 **0.04→0.71** 的硬跳变」。

实测：两人 2.0m/2.01m 时虽无连边，但 `r_gcc` = 最大连通分量占比 = 1/2 = **0.5**（不是 0），score = 0.4×0.1 + 0.3×0 + 0.3×0.5 = **0.19**。正确表述应为「**0.19→0.71** 硬跳变」。

方向结论（存在 2m 边界硬跳变）不变，但 0.04 是**错误数值**。答辩时评委若追问边界值，报告会当场露怯。建议 A2 修正，并把边界用例（1.99m / 2.00m）加入黄金测试。

## 最高价值质疑（Top 5，供总负责人决策）

1. **【P0 升级】P1-1 评分倒挂必须升级为 P0**：问题位于唯一生产决策路径（FSM），常见输入（两人 <2m、重复检测点）即可触发，且与规则引擎「DANGER 需 n≥10」语义直接冲突，答辩可现场复现。A2「无 P0」的判据不适用。
2. **【P0 新证据】重复点/重合点导致图拉普拉斯饱和，A2 完全漏报**：同坐标重复点 score=0.7067→DANGER，C++ 生产链不去重同样触发。这是 P1-1 的工程必现触发源，必须并入 P0 修复范围并补黄金用例。
3. **【P1 假防线】DBSCAN 标签反转的「测试复刻版」本身用错哨兵值**：`test_crowd_dbscan.py:379` 硬编码 `UNCLASSIFIED,NOISE = -1,-2`，与 C++ 头文件相反，导致反转被测试掩盖。修复成本=Python 常量 + 3 处 docstring + 复刻版常量 + 新增跨语言黄金用例，比 A2 说的多一处。
4. **【P1 论文可复现性】Kalman 幽灵点直接污染消融脚本**：`ablation_study.py:73-75` 全量使用含漏检外推的 `states()`，论文数据基于 Python 独有语义，板端复现不出；与 C++ 生产链语义分叉。应优先修复并重跑消融。
5. **【P1 回归风险】A2 修复建议未做黄金数据影响评估**：n_ref≥50 会翻转 `risk_fsm.json` 现有用例等级（0.81→0.63，DANGER→WARNING）；改 density 归一化会整体推翻 graph_laplacian 黄金数据与规则引擎口径。应采用「n<3 门控 + 文档化」组合，禁止短期改 density。

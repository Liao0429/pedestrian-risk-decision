## 1. 质疑点④：测试统计数字核对

## 3. 质疑点①核心：哪个 P1 最可能被答辩评委问出破绽？

**判断：评分校准倒挂，且不是 A6 描述的"边界场景"，而是生产数据的系统性行为。**

A6 只算了理论数值（0.7067 vs 0.61），没有检查生产结果数据。我作为数据专家对 `results/rerun/video_enhanced/` 全部 111 条时间线（45021 帧，与 README 完全一致）做了 DANGER 帧的 n 分布统计：

| 统计项 | 数值 |
|---|---|
| DANGER 帧总数 | 11748（与 README 一致） |
| n=0 的 DANGER 帧 | 173（FSM 保持帧） |
| n=1 的 DANGER 帧 | 1075（保持帧） |
| **n=2 的 DANGER 帧** | **2793（23.8%）** |
| **n≤3 的 DANGER 帧** | **5294（45.0%）** |
| **其中"两人紧密"画像（n=2, density=1.0, r_gcc=1.0, fiedler=2.0）** | **2566 帧（21.8%）**——正是 A6 理论示例的精确画像 |
| 出现"两人紧密触发 DANGER"的视频数 | 46/66 条 |
| 极端案例 | mixkit_4530：529 帧 DANGER 中 525 帧由两人紧密触发（99.2%） |
| 基线（规则引擎）DANGER 帧 n 分布 | 2190 帧，**最小 n=10，全部 n≥10** |

**为什么这是答辩最大破绽：**
1. **数据自相矛盾**：README 声称"谱特征提升高风险识别 +9558 帧（2190→11748）"，但增强后 DANGER 帧中 45% 的 n≤3、21.8% 是两人紧密场景，而基线 DANGER 全部 n≥10。评委若问"增强多出来的 DANGER 帧是什么场景？"，答案里 1/5 是"两个人站得近"。
2. **答辩高频问题**："你的 DANGER 报警在什么条件下触发？两个人也会报警吗？"——这是风险分级系统最自然的问题。项目自己的结果数据（46/66 条视频、2566 帧）会直接暴露，学生目前没有准备（README/论文未披露 DANGER 帧的 n 分布）。
3. **A6 的修复建议（n<3 不得 DANGER / 单调性断言）其实触及了设计裁决**：当前行为与项目文档"10 人分散不危险，6 人挤门口危险"（导读.md:16）的"局部聚集"语义并不矛盾——两人 0.5m 是最高密度聚集。因此这不是简单 bug，而是**未文档化的校准选择**。学生必须先想清楚"两人紧密是否应判 DANGER"，再决定改代码还是改文档，否则答辩时前后矛盾。

**风险排序（被问概率 × 破绽不可辩护度）：**
- **评分倒挂**：被问概率高（算法语义，数据可见），不可辩护度中高（涉及设计裁决，目前无文档）→ **最危险**
- RKNN 返回值：被问概率中（"NPU 失败会怎样"），不可辩护度高（真 UB、无任何辩解空间）→ 次之
- 标签反转：被问概率低（需评委对比 C++/Python 源码），一旦问出不可辩护（测试还"保证"了它）→ 再次
- SPI CS：被问概率极低（硬件细节、非主链路）→ 最安全

**建议（按答辩收益排序）：**
1. 立即统计并披露 DANGER 帧的 n 分布（论文/README 加一段"等级基于局部聚集密度而非人数门槛；DANGER 帧中 21.8% 为两人紧密场景"）——把暗雷变成明牌。
2. 明确裁决语义并锁定：要么接受"两人紧密=DANGER"（写文档 + 加回归测试 + 加黄金场景），要么加门控（如 n<3 不得 DANGER）并**重跑全部实验**（因为会影响 11748/66 条等所有关键数字）。
3. 把该边界用例加入 `test_risk_fsm.py` 与黄金数据（A6 P1-3 建议成立，但应升级为最高优先级）。

## 4. 质疑点②：CI 门禁建议是否过度工程？

**判断：A6 的 CI 门禁建议是"企业级 CI 思维"与"毕设投入产出"的混合体——轻量三项应采纳，重资产三项过度工程。**

**应采纳（成本≈一行配置，收益明确）：**
- push 分支加 `review-opt-*`（ci.yml 一行）：当前审查分支 push 不触发 CI，确实影响开发闭环。
- 加 `workflow_dispatch`（一行）：手动触发入口，零维护成本。
- cpp-tests 装 `libopencv-dev`（一行 apt）：否则 test_risk_config 两个 OpenCV 用例在 CI **永远被编译成 SKIP 桩**（我已验证 `#if HAS_OPENCV` 机制），A6 P2-3 属实。

**过度工程（不建议在毕设做）：**
- **自托管 runner + Luckfox SDK 缓存 + 板端冒烟 job**：需要常驻机器、runner 维护、硬件接入与抖动处理，对一个单人、单板、短期项目是持续负担。学生已有"真机 28h 长稳 + 手动冒烟"流程（EDGE_TEST_REPORT 存在）。更优替代：在仓库里放一份 **板端人工冒烟清单 + 交叉编译脚本**，答辩前按清单执行即可获得同等说服力。
- **覆盖率门禁 ≥80%**：main.cc 依赖 RKMPI 无法主机编译，覆盖率天然低，门禁只会逼出"为覆盖率而覆盖率"的假测试。覆盖率应作为报告（`coverage.py` 输出）而非合入门禁。
- **qemu-arm NEON job**：成本高（qemu 环境 + 交叉工具链 + 不稳定），收益低。NEON 一致性用板端手动跑一次 `test_preprocess_neon` 即可（顺便解决它无构建目标的问题）。

**CMake ctest job（P2-2）**：中等价值。CMakeLists 确实只有 5 个 target，README"等价 CMake 方式"的声明不成立。但最低成本修法是**改 README 声明**（"CMake 支持主机测试子集"），而不是补 6 个 target + ctest job。时间允许再补。

**建议**：门禁建议精简为"3 个轻量改动 + 1 份板端人工清单 + README 声明修正"，重资产三项明确不做。把省下的时间投入 §3 的评分校准问题。

## 5. 质疑点③：补测用例优先级是否合理？

**判断：A6 的优先级方向正确，但应按"答辩风险 × 修复成本"重排——评分校准应提到 RKNN 之上，SPI 和主循环注入应后置。**

| 优先级 | 用例 | 我的理由 |
|---|---|---|
| **P0（立即，成本低）** | ① 评分校准回归：两人 0.5m 等级断言 + 三人链单调性/门控 + 进黄金数据 | 数据实证影响 21.8% DANGER 帧；纯 Python，半天内可完成；同时补 README n 分布披露 |

| **P2（有时间再做）** | ⑥ SPI 多段事务接口 + FakeSpi CS 状态机 | 主流水线不用 LCD/触摸，答辩风险低；若论文宣称触摸/LCD 功能则升 P1 |

- A6 P1-5（主循环异常路径）建议的"可注入主循环单测"是毕设级重构，应降级为人工清单。

## 6. 结论

A6 报告质量高：**所有测试统计数字经独立复跑全部正确**，4 个代码缺陷全部属实，测试盲区的判断（"测试与缺陷共享同一套假设/常量"）一针见血。但作为数据专家，我补充三点修正：
1. **评分倒挂不是边界用例，是生产数据的系统性行为**（21.8% DANGER 帧为两人紧密触发，基线 DANGER 全部 n≥10）——这是答辩最大破绽，优先级应最高。
2. **4 个 P1 中 SPI 与标签反转不在主链路**，应降 P2，避免资源错配。
3. **CI 门禁建议取轻量三项，弃重资产三项**，毕设场景用板端人工清单替代自托管 runner 与覆盖率门禁。

## 7. 最高价值质疑（3~5 条）

1. **【评分倒挂是数据现象而非边界用例】** A6 只算了理论值。我统计 `results/rerun/video_enhanced` 111 条时间线：11748 个 DANGER 帧中 **n≤3 占 45.0%、"两人紧密"（n=2, density=1, fiedler=2）占 21.8%（2566 帧）、46/66 条视频出现**；而基线 DANGER 2190 帧全部 n≥10。答辩中"为什么两个人站得近就 DANGER？"是最可能被问出的破绽。**建议：立即披露 DANGER 帧 n 分布 + 明确裁决语义（接受并文档化，或加门控并重跑实验）+ 补回归测试。**
2. **【A6 的"四个 P1"只有两个在主链路】** RKNN 返回值与评分倒挂是生产主链路 P1；SPI CS 属附件驱动（main.cc 零引用）、crowd_dbscan 标签反转属未集成的预留头文件（全工程零引用、从未被编译），均应降 P2。A6 并列 P1 会误导答辩准备。
3. **【952 是最大口径，CI 实际跑不到；另有一个构建孤儿】** test_risk_config 的 OpenCV 用例在 CI 被 `#if HAS_OPENCV` 编译成 SKIP 桩，A6"CI 上 952 项断言"表述夸大；`test_preprocess_neon.cc` 不在任何 Makefile/CMake 目标中，A6 未列此盲区。**数字本身（191/187+4/912/952）全部复跑无误。**
4. **【CI 门禁一半过度工程】** 分支触发、workflow_dispatch、libopencv-dev 三个轻量改动应采纳（一行成本）；自托管 runner + 板端冒烟 job、覆盖率门禁 ≥80%、qemu-arm 对毕设是过度工程，应用"板端人工冒烟清单 + 交叉编译脚本"替代。
5. **【补测优先级应重排】** 评分校准回归（P0，成本半天、影响 22% DANGER 帧）应提到 RKNN 失败注入之上；RKNN 先修两行代码再谈单测；SPI 多段事务与主循环可注入测试后置；标签反转与 Python 配置校验成本极低、应立即做。
